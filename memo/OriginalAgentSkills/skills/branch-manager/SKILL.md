# branch-manager

## 概要
本スキルは、book2pdf プロジェクトの feature ブランチ運用を一元管理します。

## 原則
- **1 つのブランチは 1 つのタスク専用とし、複数のタスクにまたがって利用しない**

## ブランチ命名規則

```
feature/<タスクNo>-<タスクのタイトル>
```

- 例: `feature/FE002001-進捗表示 UI の実装`
- 例: `feature/BE007001-FastAPI に CORS ミドルウェアを追加する`

詳細は `references/branch-naming.md` を参照する。

## 通常運用手順

1. **ブランチ作成**
   - `git checkout main && git pull && git checkout -b feature/<タスクNo>-<タスクのタイトル>`
   - 作成前に `git branch -a` で同名の未マージブランチがないことを確認する

### 作業開始前のブランチ健全性確認

feature ブランチで作業を開始・再開する前、必ず以下を実施する：

1. **main との差分を確認する**
   - `git fetch origin`
   - `git log --oneline HEAD..main`
   - `git diff --stat HEAD main`

2. **main から遅れている場合は、作業前に main をマージする**
   - `git checkout main && git pull`
   - `git checkout feature/<タスクNo>-<タスクのタイトル>`
   - `git merge main`
   - コンフリクト発生時は解消してから作業を開始する
   - マージ後に再度 `git log --oneline HEAD..main` を実行し、遅れが解消したことを確認する

3. **作業再開時の確認項目**
   - `git branch --show-current` で対象ブランチであることを確認
   - `git status` で working tree が clean であることを確認
   - `git log --oneline -5` で期待する履歴であることを確認

2. **作業・コミット**
   - すべての作業は feature ブランチ上で行う。`main` ブランチへの直接コミットは禁止。
   - コミット前には、以下の形式でユーザーに選択式で確認する
     - 「コミットを実行します。よろしいでしょうか？ **A. はい** / **B. いいえ**」
     - ユーザーが「A. はい」を選択した場合のみ実行する
   - コミット: `git add -A && git commit -m "[<タスクNo>] <内容>"`

3. **ユーザーによるマージ前チェック・マージ承認**
   - マージを実行する前に、以下のすべてを満たしていることを確認する
     - `.clinerules` の「タスク完了基準」をすべて満たしている
     - **ユーザーからの UAT に対する明示的な合格発言**（UAT 要タスクの場合）
     - **Gate 3 でユーザーに承認依頼を実施して承認を得ている**（必要な場合）

4. **マージ**
   - マージ前には、以下の形式でユーザーに選択式で確認する
     - 「main ブランチへマージします。よろしいでしょうか？ **A. はい** / **B. いいえ**」
     - ユーザーが「A. はい」を選択した場合のみ実行する
   - `git checkout main && git pull && git merge --no-ff feature/<タスクNo>-<タスクのタイトル>`

5. **push**
   - push 前には、以下の形式でユーザーに選択式で確認する
     - 「リモートへ push します。よろしいでしょうか？ **A. はい** / **B. いいえ**」
     - ユーザーが「A. はい」を選択した場合のみ実行する
   - `git push origin main`

## feature ブランチの削除

AI は、`git branch -d` および `git branch -D` を**自分の手で実行してはならない**。

ブランチの削除に関する判断・実行は、すべてユーザーに委ねる。

ユーザーから「ブランチを削除してください」との**文字通りの指示**を受けた場合でも、AI は削除コマンドをテキストで提示するにとどめ、**コマンドを実行しない**。

提示する際は、以下の注意事項も併記する。

> **注意**: マージ後に追加修正が必要になる可能性があります。本当に削除してよろしいですか？

提示例：

```text
ブランチの削除はユーザー自身で実行してください。
以下のコマンドを手動で実行してください。

git branch -d feature/XXX-YYYYY

**注意**: マージ後に追加修正が必要になる可能性があります。本当に削除してよろしいですか？

実行後、次の指示をお待ちしています。
```

AI が誤ってブランチを削除した、または削除しようとした場合は、**直ちにユーザーに報告し、以降の作業を停止する**。

## マージ前最終承認チェックリスト（絶対遵守）

マージを実行する前に、以下の条件が**すべて**満たされていない場合、**マージを絶対に実行してはならない**。

- [ ] **ユーザーからの UAT に対する明示的な合格発言**（UAT 要タスクの場合）
  - 「いいね」「OK」「了解」などの曖昧な承認では不十分
  - 「UAT合格」「問題ない」「承認する」などの明確な意思表示が必要
- [ ] **`<識別子>-TASKS.md` の【タスク完了日付】欄に日付が記入されていること**
  - **git log にマージコミットが存在しても、タスク管理表に完了日付がない場合は「未完了」とみなす**
  - 完了日付は、`.clinerules` の「タスク完了基準」をすべて満たした後に限り記入する
- [ ] **Gate 3 でユーザーに最終結果と検証テスト結果を提示し、承認を取得していること**（必要な場合）

## マージブロック条件

以下のいずれかに該当する場合、**マージを中止する**。

| ブロック条件 | 確認方法 | 該当時の対応 |
|---|---|---|
| UAT 要タスクで、ユーザーからの合格発言がない | `<識別子>-TASKS.md` の実施結果欄やワークログ、または直近の会話履歴を確認 | ユーザーに UAT 結果を確認し、明示的な合格発言を求める |
| タスク管理表に完了日付が記入されていない | `<識別子>-TASKS.md` の【タスク完了日付】欄を確認 | Phase 3 の検証が完了していない可能性がある。検証を実施する |
| Gate 3 の承認を取得していない | 直前の会話履歴を確認 | Gate 3 でユーザーに最終報告を提示し承認を得る |
| `git log` やブランチの存在のみで「完了済み」と判断している | 上記 3 点の照合を実施 | **git 履歴の存在 ≠ タスク完了**。必ずタスク管理表とユーザー承認を照合する |

**重要:** `git branch -a` で feature ブランチが消失している、または `git log` にマージコミットが存在するだけでは、上記ブロック条件が解除されたことを示さない。必ずタスク管理表とユーザー承認を照合すること。

## タスク管理表との照合義務

タスクが「完了した」と判断する前に、以下の 3 点を**すべて**確認しなければならない。

1. **コード・テストの完了確認**
   - ビルドがエラー 0 件で PASS しているか
   - 単体テストが失敗 0 件で PASS しているか
   - 動作確認が期待結果と一致しているか

2. **ユーザー承認の確認**
   - Gate 3 でユーザーから承認を取得しているか
   - UAT 要タスクの場合、ユーザーからの明示的な合格発言があるか

3. **タスク管理表との照合**
   - `<識別子>-TASKS.md` の【タスク完了日付】欄に日付が記入されているか
   - **git log にマージコミットが存在しても、タスク管理表に完了日付がない場合は「未完了」とする**

### 矛盾発見時の対応

| 矛盾 | 対応 |
|---|---|
| git log にマージコミットがあるが、タスク管理表に完了日付がない | **マージを巻き戻すか、ユーザーに確認する**。AI は「完了」と判断してはならない |
| タスク管理表に完了日付があるが、Gate 3 の承認記録がない | **ユーザーに事実確認を行う** |
| タスク管理表に完了日付があるが、UAT 要タスクで合格発言がない | **UAT 未完了として扱い、ユーザーに確認する** |

## よくある境界ケース

- 未コミットの変更がある場合は先にコミットまたは stash する
- `docs/` 配下の変更は必ずユーザー承認を取得する
