# branch-manager

## 概要
本スキルは、book2pdf プロジェクトの feature ブランチ運用を一元管理します。
ブランチ作成・命名・マージ・削除、およびマージ済みブランチへの追加実装フローを定めます。

`.clinerules` で定義された「タスク完了基準」と「UAT 実施要否判定ガイド」を正とし、ブランチ視点での手順を補足します。

## ブランチ命名規則

```
feature/<タスクNo>-<内容の短縮名>
```

- 例: `feature/OT001001-scaffold`
- 例: `feature/FE002001-fix-download-pdf`

詳細は `references/branch-naming.md` を参照する。

## 通常運用手順

1. **ブランチ作成**
   - `git checkout main && git pull && git checkout -b feature/<タスクNo>-<内容の短縮名>`
   - 作成前に `git branch -a` で同名ブランチがないことを確認する

2. **作業・コミット**
   - すべての作業は feature ブランチ上で行う。`main` ブランチへの直接コミットは禁止。
   - コミット: `git add -A && git commit -m "[<タスクNo>] <内容>"`

3. **マージ前チェック**
   - マージを実行する前に、以下のすべてを満たしていることを確認する
     - `.clinerules` の「タスク完了基準」をすべて満たしている
     - ユーザーからの UAT 合格発言（UAT 要タスクの場合）
     - `Gate 3` 承認（必要な場合）

4. **マージ**
   - `git checkout main && git pull && git merge --no-ff feature/<タスクNo>-<内容の短縮名>`

5. **後片付け**
   - マージ後、不要となった feature ブランチを削除する: `git branch -d feature/<タスクNo>-<内容の短縮名>`
   - リモート同期: 必要に応じて `git push origin main`

## マージ前最終承認チェックリスト（絶対遵守）

マージを実行する前に、以下の条件が**すべて**満たされていることを確認する。
**いずれかが欠けている場合、マージを絶対に実行してはならない。**

- [ ] **ユーザーからの UAT 明示的合格発言**（UAT 要タスクの場合）
  - 「いいね」「OK」「了解」などの曖昧な承認では不十分
  - 「UAT合格」「問題ない」「承認する」などの明確な意思表示が必要
- [ ] **`<識別子>-TASKS.md` の【タスク完了日付】に日付が記入されていること**
  - **git log にマージコミットが存在しても、タスク管理表に完了日付がない場合は「未完了」とみなす**
  - 完了日付は、`.clinerules` の「タスク完了基準」をすべて満たした後に限り記入する
- [ ] **Gate 3 でユーザーに最終結果と検証テスト結果を提示し、承認を取得していること**（必要な場合）

## マージブロック条件

以下のいずれかに該当する場合、**マージを中止する**。

| ブロック条件 | 確認方法 | 該当時の対応 |
|---|---|---|
| UAT 要タスクで、ユーザーからの合格発言がない | `<識別子>-TASKS.md` の実施結果欄やワークログ、または直近の会話履歴を確認 | ユーザーに UAT 結果を確認し、明示的な合格発言を求める |
| タスク管理表に完了日付が記入されていない | `<識別子>-TASKS.md` の【タスク完了日付】欄を確認 | Phase 3 の検証が完了していない可能性がある。検証を実施する |
| Gate 3 の承認を取得していない | 直前の会話履歴を確認 | Gate 3 でユーザーに最終報告を提示し承認を得る |
| `git log` やブランチの存在のみで「完了済み」と判断している | 上記 3 点の照合を実施 | **git 履歴の存在 ≠ タスク完了**。必ずタスク管理表とユーザー承認を照合する |

**重要:** `git branch -a` で feature ブランチが消失している、または `git log` にマージコミットが存在するだけでは、上記ブロック条件が解除されたことを示さない。必ずタスク管理表とユーザー承認を照合すること。

## マージ済みブランチの追加実装フロー

既に `main` にマージされたタスクに追加実装が必要になった場合（UAT 中の新たな問題発見等）、以下の流れを厳守する。

**絶対に `main` ブランチ上で直接追加実装を行わない。**

### ブランチの扱い

| 状況 | ブランチ運用 |
|---|---|
| マージ済み feature ブランチが **ローカル・リモートに残存している** | そのブランチを再利用し、追加修正をコミットしてから再マージする |
| マージ済み feature ブランチが **削除済み** | 同じタスク番号でブランチを新規作成する |
| タスク管理表に **完了日付が記入済み** の場合 | 追加実装前に、タスク管理表の完了日付を **削除** し、【実施結果】欄に「マージ後追加修正実施」の旨を追記する |

### 補足：同一タスク番号のブランチ再作成について

`.clinerules` に「同一タスク番号のブランチを再作成しない」ルールがあるが、これは**未マージの重複ブランチ作成を防ぐ目的**である。マージ済みタスクへの追加実装はこの例外にあたり、同じタスク番号での再作成を許可する。

## タスク管理表との照合義務

タスクが「完了した」と判断する前に、以下の 3 点を**すべて**確認しなければならない。

1. **コード・テストの完了確認**
   - ビルドがエラー 0 件で PASS しているか
   - 単体テストが失敗 0 件で PASS しているか
   - 動作確認が期待結果と一致しているか

2. **ユーザー承認の確認**
   - Gate 3 でユーザーから承認を取得しているか
   - UAT 要タスクの場合、ユーザーからの明示的な合格発言があるか

3. **タスク管理表との照合**
   - `<識別子>-TASKS.md` の【タスク完了日付】欄に日付が記入されているか
   - **git log にマージコミットが存在しても、タスク管理表に完了日付がない場合は「未完了」とする**

### 矛盾発見時の対応

| 矛盾 | 対応 |
|---|---|
| git log にマージコミットがあるが、タスク管理表に完了日付がない | **マージを巻き戻すか、ユーザーに確認する**。AI は「完了」と判断してはならない |
| タスク管理表に完了日付があるが、Gate 3 の承認記録がない | **ユーザーに事実確認を行う** |
| タスク管理表に完了日付があるが、UAT 要タスクで合格発言がない | **UAT 未完了として扱い、ユーザーに確認する** |

## よくある境界ケース

- 未コミットの変更がある場合は先にコミットまたは stash する
- `docs/` 配下の変更は必ずユーザー承認を取得する
- マージ後にブランチを削除してもよいが、追加実装の可能性がある場合は一時的に保持してもよい
