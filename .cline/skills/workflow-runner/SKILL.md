# workflow-runner

## 概要
本スキルは、タスクの実行を以下の 4 フェーズで統一します。

1. **Phase 1: コンテキスト読込・タスク解析**
2. **Phase 2: スキル選択・実行計画**
3. **Phase 3: 実装・検証**
4. **Phase 4: 最終報告・後処理**

`.clinerules` で定義された **Skill Selection Matrix (3-layer)** と **承認ゲート** に従い、必要最小限のスキルを選択して読み込み、ユーザー承認を得ながら進めます。

## モジュール識別子
本スキルで参照するモジュール識別子（2文字）とその対応は `.clinerules` の **Task Identifier Rules** を正とします。
簡易対応は以下の通りです。

- `SY` … System / 全体設計・仕様・横断基盤・横断実装・結合テスト
- `BE` … backend
- `FE` … frontend
- `OW` … ocr-worker
- `LA` … localapp
- `OT` … Other / その他

詳細な定義、選択基準、具体例は `.clinerules` を参照してください。

## 前提（厳守事項）

- **原則として 1 タスク 1 ブランチを厳守すること。**
  - 1 つの feature ブランチ内で複数のタスクを混在させず、各タスクは開始から完了まで専用のブランチを使用すること。
  - feature ブランチの命名、マージ、削除（ユーザーが手動で実施）、追加実装の詳細な手順は `branch-manager` スキルを参照する

## 手順

### Phase 1: コンテキスト読込・タスク解析

1. `.clinerules` を読み込み、プロジェクトルールを確認する
2. タスクの識別子（`SY` / `BE` / `FE` / `OW` / `LA` / `OT`）を判定する
3. **タスク番号を確認または発行する**
   - 該当するタスク管理ファイルを読み込む
   - 既存のタスク番号と重複しないように、未使用の通番を選定する
   - 起票が必要な場合は `<識別子>-TASKS.md` に事前に記録する
4. 関連するドキュメント・コードを読み込み、タスクの背景と要件を整理する
   - `SY` → `docs/SY-TASKS.md`
   - `OT` → `docs/OT-TASKS.md`
   - 各モジュール → `<module>/docs/<識別子>-TASKS.md`
5. 不明点があればユーザーに確認し、必要に応じて調査スキル（`search_codebase`, `fetch_web_content`）を併用する
6. **重複作業を防止する（詳細は `branch-manager` スキルを参照）**
   - 既存の `git branch -a` 一覧を確認し、同名・同タスク番号の未マージ feature ブランチが存在しないことを検証する
   - 既存の `git log --oneline` を確認し、同じタスク番号で既に完了（タスク管理表に完了日付あり）していることを検証する
   - 重複が疑われる場合は、ユーザーに確認のうえ既存ブランチを再利用または整理する
7. **feature ブランチの健全性を確認する（詳細は `branch-manager` スキルを参照）**
   - `.clinerules` の **Branch Health Check Rules** に従い、以下を実行する：
     - `git branch --show-current`
     - `git status --short`
     - `git fetch origin`
     - `git checkout main && git pull`
     - `git checkout feature/<タスクNo>-<タスクのタイトル>`
     - `git log --oneline HEAD..main`
     - `git diff --stat HEAD main`
   - `main` から遅れている場合は、ユーザーに報告のうえ `git merge main` を実施する
   - マージ後に再度 `git log --oneline HEAD..main` を実行し、遅れが解消したことを確認する
   - 未コミット変更がある場合は、先にコミットまたは stash する
8. **Gate 1**: ユーザーに「タスクの理解」と「進め方の方向性」を提示し、承認を取得する
   - Plan モード・Act モードのいずれの場合も、Gate 1 をスキップしない
   - タスク完了後に別のタスクへ移行する場合は、新規タスクについて Phase 1 から Gate 1 を取得する
   - 下記の「タスク着手時確認テンプレート」を用いて、各 Phase の概要と本タスクでの想定される流れを提示する

### Phase 2: スキル選択・実行計画

1. `.clinerules` の **Skill Selection Matrix (3-layer)** に従い、必要なスキルを選択する
   - Layer 1: モジュール接頭辞に応じた必須スキル
   - Layer 2: 活動タイプ（`I`=調査, `D`=設計, `C`=コーディング, `R`=レビュー, `T`=テスト）に応じた追加スキル
   - Layer 3: 承認ゲートの通過タイミングを確認
2. 選択したスキルの `SKILL.md` を読み込む
3. 実施手順・確認項目・リスクを整理し、`<識別子>-TASKS.md` の【計画】欄や `<識別子>-WORK-LOG.md` の【実施予定】に記録する
4. **Gate 2**: ユーザーに具体的な実行計画を提示し、承認を取得する
   - Plan モード・Act モードのいずれの場合も、Gate 2 をスキップしない
   - タスク完了後に別のタスクへ移行する場合は、新規タスクについて Phase 2 から Gate 2 を取得する
   - 下記の「タスク着手時確認テンプレート」に基づき、本タスクでの想定される流れを含めた実行計画を提示する

### Phase 3: 実装・検証

1. 承認された計画に沿って実装・設計・調査を実行する
2. 節目ごとにユーザーに状況を報告し、方向性のズレがないか確認する
3. **実装完了後、必ず結果の正常確認を実施する**（ビルド・テスト・検証・動作確認）
   - **ビルドテスト**: 対象モジュールのビルド/コンパイルを実施し、エラー 0 件・警告は許容範囲内になるまで繰り返し実施する
   - **単体テスト**: 既存および新規のテストスイートを全件実行し、失敗 0 件・スキップ 0 件（意図的スキップを除く）になるまで繰り返し実施する
   - **動作確認**: 主要ユースケースおよびユーザー検証項目を満たす自動テストを実施し、期待結果と実際の結果が完全に一致することを確認する
4. 問題があれば即座に修正し、再度検証する。いずれのテストフェーズも PASS するまでは Phase 3 を完了としない
5. ドキュメントの更新も必要に応じて実施する（ただし `docs/` 配下の変更はユーザー承認が必要）
6. **Markdown テーブルの検証**: `*-TASKS.md` や `docs/**/*.md` のパイプテーブルを変更した場合は、`markdown-table-validator` スキルに従いカラム整合性を検証する

#### Phase 3-A: 他モジュール不具合発見時の対応

タスク実行中に現在の対象モジュール以外の不具合が発見された場合の対応フロー。

1. **即座に中断**: 現在のタスクの実装・検証を一時中断する。
2. **発見元モジュールのタスク登録**: 不具合が発生したモジュールに対して、規定のワークフロー（Phase 1〜Phase 2・Gate 1/2 承認）に従ってタスクを登録する。
3. **影響評価と優先順位の決定**:
   - **ブロッキング（対応中タスクの完了を妨げる）**: 追加された他モジュールのタスクを現在のタスクより優先し、先に完了させる。現在のタスクは中断状態として `<識別子>-TASKS.md` に「不具合発見元: <現在のタスク番号>」を記録しておく。
   - **非ブロッキング（対応中タスクの完了に影響しない）**: 追加された他モジュールのタスクは「タスク登録まで」とし、Phase 1〜Phase 2（Gate 1/2）を実施して終了する。その後、現在のタスクを Phase 3 から継続して完了させる。
4. **記録**: どちらの場合も、`<識別子>-TASKS.md` と `<識別子>-WORK-LOG.md` に起票記録を残し、不具合発見元のタスク番号を参照として記載する。
5. **UAT フェーズでの適用**:
   - UAT（ユーザー検証テスト）実施中に他モジュールの不具合が発見された場合も本フローに従う
   - 不具合が UAT 合格の阻害要因となる場合、元の UAT タスクは合格判定せず、該当不具合の解決を待つ
   - 他モジュールのタスク登録時は【計画】欄に「UAT 不具合発見元: <元タスク番号>」を明記する
   - 不具合解決後、元の UAT タスクを再開し改めて UAT を実施する

### Phase 4: 最終報告・後処理

1. **最終報告書を作成する**:
   Phase 4 の最終報告書は、`.clinerules` で定義された **Phase 4 必須報告ルール** に従い、以下の項目を漏れなく記述して作成すること。

   - **実装完了までの工程推移実績要約**
   - **変更ファイル一覧**
   - **テストフェーズ毎の実施済みテスト項目と合否判定結果**（ビルド / 単体テスト / 動作確認）
   - **テスト環境準備状況について**
   - **ユーザーテスト項目と実施方法について**
   - **実装時に出てきた注意事項**
   - **残タスク**

   テスト結果および環境準備、ユーザーテストの詳細な記述形式や合否判定基準は、必ず `test-manager` スキルの **Verification Report Template** を参照し、そのフォーマットをそのまま適用すること。
2. **ユーザー検証テストの実施（該当する場合）**:
   ユーザー検証テストを要するタスクでは、最終報告書に記載した「テスト環境準備状況」と「ユーザーテスト項目と実施方法」に基づき、ユーザーが検証を実施できる状態を整備する。ユーザーが実際に検証を完了し、明示的に合格を出すまでタスクを完了としない。
3. **Gate 3**: 破壊的変更を含む場合、または `docs/` 配下の変更がある場合、またはユーザー検証テストを要する場合は、ユーザーに最終結果と検証テスト結果を提示し承認を取得する
4. **完了基準チェック**: `<識別子>-TASKS.md` の【タスク完了日付】欄に日付を記入する前に、以下をすべて満たしていることを確認する。満たしていない場合は完了日付の記入を禁止し、代わりに【実施結果】欄に中間進捗を追記する。
   - [ ] Phase 3 の **ビルドテスト**・**単体テスト**・**動作確認** がすべて PASS
   - [ ] 必要な場合は **Gate 3 でユーザーに承認依頼を実施して承認を得ている**
   - [ ] **ユーザー検証テスト（UAT）が必要なタスク**では、ユーザーから明示的な合格を得ている
   - [ ] **マージブロック条件チェック**: `branch-manager` スキルのマージブロック条件に該当しないことを確認している
   - [ ] Git merge 完了
5. 承認を得たら以下の後処理を実施する:
   - `<識別子>-TASKS.md` の【実施結果】に追記
   - `<識別子>-WORK-LOG.md` に【実施実績】セクションを追記
   - `<識別子>-CAVEATS.md` に注意事項を追記（該当する場合）
   - **完了基準チェックを満たしている場合のみ**、`<識別子>-TASKS.md` にタスク完了日付を記載
6. Git 運用（プロジェクト方針に従う）:
   - 作業開始前: `git status` で未コミット変更を確認する。未コミットの変更がある場合は先にコミットするか、ユーザーに確認して stash / 無視（ユーザー個人メモ等）を決定する
   - **ブランチ運用**: ブランチ作成・マージ・削除（ユーザーが手動で実施）・追加実装の詳細は `branch-manager` スキルを参照する。原則として 1 タスク 1 ブランチを厳守する
   - コミット: `git add -A && git commit -m "[<タスクNo>] <内容>"`
   - **マージ前**: `branch-manager` スキルの「マージ前最終承認チェックリスト（絶対遵守）」でブロック条件を確認する
   - マージ前に `git log --oneline main..feature/<タスクNo>-<タスクのタイトル>` を実行し、feature ブランチが `main` の最新を含んでいることを確認する
   - マージ: `git checkout main && git pull && git merge --no-ff feature/<タスクNo>-<タスクのタイトル>`
   - リモート同期: 必要に応じて `git push origin main` または該当ブランチを push する
7. ユーザーにタスク完了を報告する
8. 続けて別のタスクを実施する場合は、本ワークフローの Phase 1 から Gate 1 / Gate 2 を取得する

## タスク着手時確認テンプレート

タスク着手時（Phase 1 完了時点）、必ず以下の汎用フォーマットを用いてユーザーに確認し、承認（Gate 1）を取得する。  
Phase 2 の実行計画提示（Gate 2）においても、本テンプレートの流れに基づいて計画を具体化して提示する。

### 各 Phase の概要

| Phase | 名称 | 主な活動 | 成果物 |
|---|---|---|---|
| Phase 1 | コンテキスト読込・タスク解析 | `.clinerules`、タスク管理表、関連ドキュメントの読み込み。モジュール識別子の判定。タスク背景・要件の整理。 | タスクの理解と方向性の提示 |
| Phase 2 | スキル選択・実行計画 | Skill Selection Matrix に従い、必要なスキルを選択・読み込み。実施手順・確認項目・リスクを整理。 | 実行計画書 |
| Phase 3 | 実装・検証 | 承認された計画に沿って実装・設計・調査を実行。節目ごとにユーザーへ状況報告。実装後、文法・リンク・整合性の検証を実施。 | 変更された成果物 |
| Phase 4 | 最終報告・後処理 | 最終報告書の作成（実施内容、変更ファイル、検証結果、残タスク）。タスク表・作業ログへの追記。Git コミット・マージ。 | タスク完了報告 |

## 選択的スキル読込ルール

- タスク開始時は必ず `workflow-runner` スキルを最初に読み込む
- 以降、Layer 1 / Layer 2 のマトリックスに従い、必要なスキルのみを追加で読み込む
- すべてのスキルを読み込む必要はない
- タスクの性質が変わった場合（例：調査タスクから実装タスクへ）は、適宜スキルを追加読み込みする
- スキルファイルを読み込む際は、必ず `read_files` で実ファイルを開き、記憶や要約に頼らないこと。

## よくある境界ケース

- 未コミットの変更がある場合は先にコミットまたは stash する
- `docs/` 配下の変更は必ずユーザー承認を取得する
- ユーザーが計画を修正・取り消しを求めた場合は、Phase 2 に戻って再計画する
- マージ後は feature ブランチを削除してもよい（プロジェクト方針に従う）
- タスクが長時間化する場合は、中間報告を挟みつつ進める
