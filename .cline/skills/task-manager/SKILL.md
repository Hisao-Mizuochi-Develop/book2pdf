# task-manager

## 概要
本スキルは、book2pdf プロジェクトのタスク管理表・作業ログの運用ルールを定めます。

## 手順

1. **タスクNo体系**
   - 形式: モジュール識別子(2桁) + ユースケースNo(3桁) + 通番(3桁)（計8文字）
   - 識別子（簡易対応）:
     - `SY` … System/全体設計・仕様・横断基盤・横断実装・結合テスト
     - `FE` … frontend
     - `BE` … backend
     - `OW` … ocr-worker
     - `LA` … localapp
     - `OT` … Other / その他
   - 詳細な定義、選択基準、具体例は `.clinerules` の **Task Identifier Rules** を参照する
   - 例: ocr-worker のユースケース003の1番目 → `OW003001`
   - 通番は各ユースケース内で 001 から連番

2. **タスク粒度**
   - 数時間〜1日以内で完了できる単位
   - 1つのタスクに複数の責務が含まれる場合は分割を検討
    - ただし、達成可能な単位を保ち、細部を無理に別タスクに分けすぎない

3. **テンプレート参照義務（必須）**
   - `<識別子>-TASKS.md` を**新規作成・更新する前**および**作成・更新時**に、必ず `references/TEMPLATE-TASKS.md` を `read_files` で読み込む
   - テンプレートに定義された構造（タイトル、ユースケース一覧、アンカー、戻りリンク、4列テーブル、タスク詳細セクションの書式）に厳密に従う
   - テンプレートと既存ファイルの構造に齟齬がある場合は、既存ファイルをテンプレート準拠に修正する

4. **記録場所**
   - タスク管理表 → `<module>/docs/<モジュール識別子>-TASKS.md`
   - 作業ログ → `<module>/docs/<モジュール識別子>-WORK-LOG.md`
   - 全体横断 → `./docs/OT-WORK-LOG.md`, `./docs/OT-TASKS.md`
   - 作業の記録はタスク詳細欄に箇条書きで記載する

5. **計画の変更**
   - 一度記載した【計画】は削除せず、追記のみ
   - 実施しない場合は、その理由を【計画】欄内に追記

6. **タスク実装方針**
   - 将来の課題も含め、原則としてすべての項目を実装する

7. **タスクの並行実行禁止**
   - タスクは並行して進めない
   - 現在のタスクが完了（Phase 4 終了・コミット）してから、次のタスクを開始する
   - ただし、チーム開発で複数の人間開発者が別々のタスクを並行して作業する場合はこの限りではない

8. **実装後の記録更新**
   - タスク完了後、`workflow-runner` スキルに従い以下を更新する
     - `<module>/docs/<モジュール識別子>-TASKS.md` の【実施結果】
     - `<module>/docs/<モジュール識別子>-WORK-LOG.md` の【実施実績】
   - 完了日付を `<module>/docs/<モジュール識別子>-TASKS.md` に記載する
   - **タスク管理表を更新した後は、`markdown-table-validator` スキルに従いパイプテーブルのカラム整合性を検証する**

9. **UAT 不具合発見時の対応**
   - 機能実装タスクの UAT で不具合が発見された場合:
     a. 元の機能実装タスクを一旦中断し、UAT 合格としない
     b. タスクタイトル「`<元タスク番号> UATバグ対応`」で新規タスクを起票する
     c. 同じ元タスク由来の複数のバグは、1 つの「UATバグ対応」タスクに集約する
     d. 「UATバグ対応」タスクを完了（Phase 4 終了）させる
     e. 元の機能実装タスクを再開し、改めて UAT を実施する
     f. ユーザーから明示的な UAT 合格発言を得て、元タスクを完了する
   - **クロスモジュールの場合**:
     - UAT 中に現在の対象モジュール**以外**の不具合が発見された場合、`.clinerules` の **Cross-Module Defect Handling** に従って対応する
     - 不具合がブロッキングの場合、元の UAT タスクを中断し他モジュールの不具合対応を優先する
     - 不具合が非ブロッキングの場合、他モジュールのタスクを登録した上で元の UAT タスクを継続する

## 10. タスク完了判定時の照合義務

タスクが「完了した」と判断する前に、以下の 3 点を**すべて**確認しなければならない。

1. **コード・テストの完了確認**
   - ビルドがエラー 0 件で PASS しているか
   - 単体テストが失敗 0 件で PASS しているか
   - 動作確認が期待結果と一致しているか

2. **ユーザー承認の確認**
   - Gate 3 でユーザーから承認を取得しているか
   - UAT 要タスクの場合、ユーザーからの明示的な合格発言があるか

3. **タスク管理表との照合**
   - `<識別子>-TASKS.md` の【タスク完了日付】欄に日付が記入されているか
   - **git log にマージコミットが存在しても、タスク管理表に完了日付がない場合は「未完了」とする**

### 矛盾発見時の対応

| 矛盾 | 対応 |
|---|---|
| git log にマージコミットがあるが、タスク管理表に完了日付がない | **マージを巻き戻すか、ユーザーに確認する**。AI は「完了」と判断してはならない |
| タスク管理表に完了日付があるが、Gate 3 の承認記録がない | **ユーザーに事実確認を行う** |
| タスク管理表に完了日付があるが、UAT 要タスクで合格発言がない | **UAT 未完了として扱い、ユーザーに確認する** |

## よくある境界ケース
- 新規ユースケースが必要な場合: まずユーザーに提案し、承認を得てから起票
